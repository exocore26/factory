Common Tool Requirements Forge

Turn a tool idea into a reusable requirements document and a development TODO — while actively testing what belongs in the Parent-Engine layer.

Design rule: describe the sub-project first; abstract the shared capability second.
This is a static, dependency-free site: suitable for GitHub Pages, GitLab Pages, or any simple web host.
Step 1 of 8Autosave: on
01 / FRAME

What are we designing?

Start with the thing a sub-project wants to build. The Forge will later look for the repeatable mechanism hidden inside it.

02 / OUTCOME

What problem does it solve?

Write this in terms of user intent, not implementation. The output should remain meaningful if the implementation changes.

03 / FLOW

Describe the transformation

Think of the tool as a bounded transformation: inputs → decisions → operations → outputs. This is the main abstraction boundary.

04 / ABSTRACT

Which reusable capability is hiding inside it?

Select every mechanism that could plausibly be shared across projects. The generator turns these into Parent-Engine candidates.

Abstraction test

Would a second unrelated sub-project need essentially the same mechanism with different content? If yes, treat it as a candidate shared capability. If only the content changes, keep the implementation in the sub-project.
